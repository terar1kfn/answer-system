# Core consistency and diagnostic logic — 0.42 (validation deferred)

This first stabilization milestone follows the static v0.41 architecture audit. It deliberately changes shared diagnostic semantics rather than adding a new student-facing feature. The native application remains untouched.

## Shared fixed evidence and applicability

Import answer-system/diagnostic-evidence for fixedOption, confirmedOptionIds, GUIDE_PREREQUISITE_QUESTIONS, isAutomaticPrerequisiteQuestion, validGuidePrerequisites and normalizeGuidePrerequisites. QUESTIONS is the authoritative bilingual fixed option registry; there is no second option vocabulary. A requirement is a conjunction of named known question keys, each with a nonempty allowed option set. Unknown/not_tried cannot establish applicability. A condition containing only those choices is invalid; a mixed set is evaluated using its confirmable values. Explicit null/malformed conditions are invalid rather than unconditional. Duplicate legacy values are treated as one option, regardless of order. Each array is bounded to 200 entries. New mapping/source drafts and reconciliation retain their existing unique-value requirement. Raw mapping rows and exact historical source/route/approval fingerprints are not rewritten; normalization applies only to derived engine metadata. An invalid native mapping requirement is withheld with INVALID_GUIDE_PREREQUISITES. Invalid standalone catalog requirements reject the catalog. The original explicit single-product native collaboration mapping gate remains mandatory.

answer-system/guide-selection provides compareGuideApplicability (disjoint, equivalent, a_more_specific, b_more_specific, overlapping), moreSpecific, potentialGuideTie and confirmedPrerequisitesMatch. These share the same confirmed condition semantics. A strict subset of allowed choices or additional required evidence can increase specificity; duplicate values cannot. A potential tie is an equivalent or incomparable overlapping pair, not a claim that a real state reaches both; a third candidate, protected routing or unavailable scope can resolve it. Both coverage and quality audit use that pair relation, and quality's bounded theoretical coverage uses the same confirmed predicate. The original selector still waits for unresolved narrower/incomparable candidates, and native policy/eligibility still takes precedence. Auto-question list and the existing question priority are shared; no added permission or protected question is introduced. Engine RULE_VERSION becomes 0.42.0. Old in-memory states are not interchangeable; retain historical outcome rule pins and do not migrate them as new evidence.

## Native guide admission

native-guide-policy supplies exact Low/Medium risk, Student/All self-service and known unreviewed-source predicates. Projection, route dependency inspection, route-review matching and audit candidate inspection reuse them. Missing, unexpected or High risk is ineligible. Medium still requires the existing route review, not automatic permission. Route review matching checks actual current dependency records and exact fingerprints; it is not authority to activate a release. Native service/card ownership, availability, reviewed-source hook, menu checks, exact product requirement, protected routing and independent release verification are still mandatory. No native catalog is supplied or imported.

## Context and AI

Shared reviewed-context definitions retain operation anchors, fixed context and existing protected-operation restrictions. They now allow meeting_product/meeting_client, portal_system and mail_client to be retained as context; this resolves the prior impossibility of recording a product prerequisite for collaboration learning. Older context shape is still accepted under prior boundaries; the new fields are optional, not authority to infer a product. A favorable proposal still requires confirmed actual prerequisites and independently verified cases, and an exact native owner/product, source and route. Learning rejects the stricter unknown/other/different/not_checked/unclear set; ordinary diagnostic prerequisites continue to use their own confirmed-choice semantics. No approved context release or activation is added here. The reviewed-context disambiguation auto-question list remains unchanged.

Ordinary initial-text and screenshot advisors share common service/domain and protected-evidence definitions and use fixedOption; each retains its distinct permitted questions, choices, privacy/consent and authorization constraints. Contextual reply uses the same fixed lookup and unconfirmed-prerequisite check but keeps its separate scope. No change to the policy gates, raw image handling, local provider or explicit confirmation.

## Bilingual display

79 additional reason messages cover previously missing diagnostic, protected, handoff and lifecycle states. Existing interfaceCopy(code,language) remains nullable for compatibility. The host should render studentInterfaceCopy(code,language) instead of raw internal codes; unknown codes return a neutral bilingual fallback. interfaceReasonCodes exposes the fixed registry keys for future coverage checks. Technical server error detail must not be shown to students. Native UI integration is not performed here.

## Deferred validation

Synthetic-only scenarios: equivalent conditions with reordered/duplicated choices; unknown-only rejection and mixed choice normalization; null and malformed prerequisites; strict subset and incomparable/disjoint overlap; pending narrower guide; consistent coverage/quality pair classification; invalid or unknown-risk native mapping/route/dependency; medium risk independent review; exact meeting-product observations and protected context rejection; legacy context compatibility; identical AI allowlists and confirmation requirements; bilingual reason registry and unknown-code fallback; old rule-version rejection and historical outcome pin preservation. Verify existing engine, mapping, route, review and learning regressions before deployment. No tests, syntax checks, models, builds, real catalog, live host changes or deployment performed.
