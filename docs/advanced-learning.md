# Advanced verified-outcome learning — 0.41 (validation deferred)

The isolated public Answer System now has a private staff-only aggregate learning/reporting contract. This is a deterministic evidence-to-review workflow, not a self-training model or an automatic update to institutional knowledge. Existing outcome ledger and native historical route verification remain authoritative. Existing reviewed-context selection rules remain unchanged.

## Required native input

The native server must build a complete scoped cohort from independently finalized, authorized records, reconciling the existing native learning service/ledger and exact historical route reviews with pre-attempt fixed observations and independently verified staff feedback. Do not accept browser-supplied rows, AI interpretations, transcripts, screenshots, identifiers derived from student IDs or raw case details. No cohort is bundled in the public repository. The new module deliberately does not import records into the existing ledger or create a second outcome store.

reportingScope is exactly {allowedGuideIds,serviceIds}, using only authorized native guide IDs and ordinary diagnostic services (identity, exam, directory, other are excluded). Scope limit 200 guides. Cohort is exactly {revision,asOf,days,complete,rows}; revision is a random opaque host snapshot revision that changes for any cohort correction or change, asOf is UTC date, days is 1–90 and complete must be true. Maximum 5,000 rows; do not silently truncate, sample or return only successes. If a complete cohort cannot be retrieved, fail closed. Include all finalized scoped attempts, including unresolved, unknown, mixed and non-attempted rows, for the specified days. One latest revision per receipt. All rows have exactly:

- caseKey, receiptKey: high-entropy opaque 24–160-character pseudonymous keys unique to case/receipt, not actual student, account or ticket identities. Same case must always use same key within the cohort. receiptKey is unique; repeated receipts fail. These keys are transient, not returned or persisted.
- revision (positive integer), day (UTC YYYY-MM-DD within the inclusive reporting window), serviceId, purpose, guideId, guideFingerprint, sourceRevision, routeFingerprint, routeAttribution, ruleVersion, completion, outcome, provenance, attribution: exact current or historical finalized fields and classified route metadata of the existing effectiveness contract. routeFingerprint may be null only for unverified_route.
- context: null or a fixed match object validated with the same operation/context allowlist as reviewed-context.mjs. The host must verify these are actual pre-attempt observations of the current original task, not post-resolution changes, guesses, unconfirmed model suggestions, or after-the-fact inferred causes. Unknown/unsupported/protected or unavailable context is represented by null, not invented observations.
- feedback: null or one of LEARNING_FEEDBACK_CODES, a separately verified staff observation associated with the same finalized attempt. No free-text note or unverified intern claim is accepted. Native capture and verification UI are not included.

verifyLearningBatch must independently verify scope, exact latest receipt revisions, cohort completeness (including unsuccessful or non-attempted records), native case grouping, finalization, route and guide attribution, actual staff verification, context timing/provenance and feedback. In particular, guide_only must exclude any other relevant interventions or attempts, including outside the current reporting scope. If verification cannot establish these conditions, reject the cohort. It cannot simply echo a supplied true flag. The wrapper revalidates format before calling the verifier and builds a fresh current native projection and route review. Immutable host snapshots and native authorization remain required; enforce rate limits, retention, privacy, safe storage and request bounds. The report only uses rows for exact currently admitted guide fingerprints/source revisions, exact current unblocked route fingerprints with authorized dependencies, staff-verified known outcomes, attempted single_native_guide paths with guide_only attribution, and cases that have exactly one finalized scoped row. This is stricter than general outcome-ledger reporting; old, mixed, branched and unverified observations are not promoted.

## Review proposals

buildAdvancedLearningReport groups distinct eligible case records by exact guide/source/route/rule identity, never pooling versions. Overall guide observations are shown only at minimumGroup (10–100). Repeated unresolved outcomes require at least minimumGroup unresolved cases and at least 35% unresolved within the group. Feedback is a separate fixed-category count, shown only if it independently meets the minimum. Context grouping uses the complete exact validated pre-attempt match object, same native owner, service/purpose, source and rule; no generalization to unobserved cases. If any observed competing guide context group is below threshold, suppress that context group rather than present only favorable comparisons. Recurring contextual failures and competing-guide groups remain review leads. A favorable exact context requires minimumGroup resolved cases, observed resolution >=90%, descriptive Wilson lower bound >=0.65, no competing observed guide in that exact context and matching current prerequisites. It is only a lead, not a probability of success or causal estimate. Where the existing guide selector confirms an actual tie without unresolved prerequisites, and all tied guides are authorized, current and same-owner, a favorable pattern can suggest an independent context-disambiguation review; otherwise only an applicability review is suggested. Existing overlapping conflicting active contexts suppress favorable proposals. No raw case IDs, observation source text, student details, staff feedback text or arbitrary generated instructions are returned. Small subgroups must remain private; the native host must protect reports and prevent differencing via overlapping scopes/time windows. Exact guide aggregate resolved/unresolved counts are paired descriptive measures, not proof of unique people or root cause.

Only proposals for human review are emitted. A context lead is not a reviewed-context candidate: independent staff must retrieve and verify individual cases, evaluate confounders and alternatives, and use the existing reviewed-context draft and native publication workflow. A failure/feedback lead must use source-verified review and the actual native knowledge editor. No automatic routing weights, learned probabilities, AI training, guide changes, model calls or publication. Proposal output is limited to 1,000 with explicit truncation; truncated reports cannot be used to prepare or decide drafts.

## Authorized review workflow

Import answer-system/advanced-learning. createAdvancedLearningReviewer requires authenticate, mayReviewKnowledge, getInput (native catalog projection contract), getReportingScope, getLearningBatch, verifyLearningBatch, mayPrepareLearningProposal, mayDecideLearningProposal, getPreparedDraft, verifyPreparedDraft, optional now. Active INTERN/MANAGER/SUPER_MANAGER role is necessary but never sufficient: each callback must enforce native permissions, scope, purpose and actor. getPreparedDraft returns the actual native stored immutable draft, and verifyPreparedDraft independently establishes the real author, exact draft, pending state and authorization. No client can invent a draft or reviewer.

report(credential,{days,minimumGroup}) returns a private report with source/catalog/mapping/scope/cohort pins and reportFingerprint. Two separately verified snapshots, including private receipt identity comparisons, must agree; authority is rechecked. prepare(credential,{proposalId,expectedReportFingerprint,days,minimumGroup}) returns a minimized author-bound pending draft for the existing native staff workflow; no storage or write is performed. The host saves only an authorized still-current draft in its private system. decide(credential,{draftRef,decision}) requires a separate authorized reviewer (not the author), exact verified native draft, current untruncated report and matching proposal. Dispositions: request_source_review, request_procedure_review, request_individual_case_review (context-success/competing only), defer or dismiss. A disposition is not publication approval. The host must atomically persist and independently recheck pins, access, draft state and deduplication before acting; the module has no mutation, replayed side effects or activation path. No endpoints, persistence, live cohort adapter or UI are implemented here.

## Deferred validation

Synthetic cases only: duplicates and corrected receipts, multiple attempts per case and mixed attribution, small groups and incomplete cohorts, stale route/guide/rule versions, current vs stale context, protected-operation exclusion, contradictory outcomes, missing observations, exact pattern matching vs unjustified generalization, staff feedback thresholds, competing small-group suppression, route authorization, competing guide scopes, author/reviewer separation, invalid or stale drafts, actor revocation, concurrent review/correction, deterministic report pins, no raw case/receipt leakage and no student-routing change. Also verify the existing reviewed-context refactor preserves all previous validation behavior. No tests, syntax checks, builds, actual learning data, providers, deployment or native-host modifications performed.
