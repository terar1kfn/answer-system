# Reviewed solution-effectiveness learning — 0.24 (validation deferred)

The new private learning service imports finalized outcomes from an existing authorized native host. It is not a student endpoint, automatic transcript learner, or evidence that a ticket closure proves success. The host supplies independent provenance verification, an authorized historical guide loader, scope checks, and a stable random receipt reference for a single guide attempt. The exact version and purpose of that guide must match the finalized record. A corrected record uses a monotonically increasing revision of the same receipt. Re-read the record and permissions before recording it. Do not import a current unfinalized conversation, screenshot, password, student identifier or arbitrary client submission.

The single-writer atomic store retains bounded guide/purpose/version metadata, a UTC day, outcome and attribution, plus an HMAC receipt digest for deduplication. It does not retain student, case or visit identifiers or raw text. The key must be held in the private host, not in source control. Treat the resulting records as pseudonymous operational data, not public anonymous data. Use a stable key for the full retention interval; do not replay old receipts after key rotation. Retention defaults to 60 days, with explicit pruning required by the host, and the reporting scope must be authorized by the native host. Enforce private filesystem ACLs, access controls, and retention operationally. The store is not multi-worker/distributed.

The report separates viewed-only or unattempted records, actual reported attempts, student-reported and staff-verified outcomes, unknown outcomes, and cases with multiple interventions or uncertain attribution. Counts represent finalized guide-attempt records, not unique students. The observed verified single-guide resolution fraction uses only known staff-verified, attempted, guide-only outcomes, is suppressed below the minimum group, and is not causal effectiveness or expected diagnostic accuracy. Other count fields are intended for authorized private staff only; do not publish them. Repeated unresolved outcomes can produce a fixed review signal, not a change to guide ranking, institutional policy, or publication.

Current guide versions are marked separately from historical versions. Previously resolved-case retrieval now requires exact native guide fingerprints when present and an explicitly verified successful outcome for a strong match; a known unsuccessful case is not a successful solution candidate. Unknown outcomes remain weak review leads. Independent case-derived pattern review and the existing guide eligibility checks remain mandatory.

No real cases, live outcome receipts, model calls, tests, builds, deployments, or private host edits have been performed. Future native wiring should use finalized ticket/visit evidence, a trusted correction workflow, approved data retention, and a scheduled host-owned pruning operation.
