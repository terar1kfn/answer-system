# Current error evidence — 0.17 (validation deferred)

A documented error code can appear after the original question, for example when a student looks at their sign-in screen or returns from a guide. The engine now proposes a bounded confirmation question before using a newly reported code. The fixed bilingual question distinguishes the current sign-in or sending operation from an earlier or unrelated one. The original service scope is preserved; a code for another service is not silently applied.

A positive confirmation records only the exact known signature and student-reported operation, not raw pasted text. Earlier screen, credential, verification and client observations may refer to another attempt and are cleared. Independently verified recovery provenance, actual attempt records and previously offered guide IDs are retained. The engine then reevaluates the normal diagnostic route. A negative or uncertain answer restores the previous route without pretending that a guide was attempted or resolved. Repeated, multiple, unrelated or ambiguous codes require clarification, and confirmation requests are bounded. Protected exam and security contexts retain precedence.

Initial conflicting codes no longer silently become a service selection that loses the error conflict. Known code extraction now handles punctuation and uses the whole bounded error-intake text instead of silently ignoring everything after the first thousand characters. Named services such as meetings remain visible in initial error classification. Reviewed factual aliases cannot override known error-code routes. Native journey deltas preserve the explicit confirmation answer using fixed labels.

The registry still recognizes only the previously documented error families. No new institutional policies, private guide content, raw OCR or credentials are retained. The engine does not assert that the code proves a root cause or authorizes an account change. No tests, builds, syntax checks, browser/provider execution, deployment, or private application changes were performed. Deferred scenarios include decline/restoration, multiple and repeated codes, new current attempts, stale prior evidence, code punctuation, protected inputs, recovery provenance, and native ticket history.
