# Evidence and alternative diagnosis — 0.14 (validation deferred)

The diagnostic engine now distinguishes a supported hypothesis, a contradicted hypothesis, a conflicting hypothesis and an untested candidate. Each rank has fixed evidence keys and relative weights. Documented error families add evidence, not proof. The uncertainty summary deliberately has no probability or verified root-cause claim. Similar scores and conflicting observations remain visible; a student-reported symptom is never an independently verified administrative finding. The rank is an explanation layer, not a permission or guide-authorization decision.

## When the first approved guide does not solve the problem

A reported negative outcome is not proof that every step was completed. For non-protected, non-MFA-setup guides, a bounded continuation distinguishes completed-but-unchanged, partial improvement, a blocked step, not attempted, changed symptom and uncertain result. The engine only offers a distinct approved purpose when a follow-up explicitly supports it, and the normal guide scope, publication, permissions and prerequisite checks still apply. It never chooses an arbitrary second search hit.

Examples of intended branches (not executed scenarios):
- A persistent mail delivery issue with no explicit restriction, but the original operation works in approved webmail: consider a distinct reviewed client/sync guide. Explicit recipient, sender, size and coded restrictions are not reinterpreted as client faults.
- General connectivity guidance failed and the remaining symptom is a missing SSID, network authentication failure or intermittent connectivity: consider the matching approved specific guide.
- An attendance scan or app issue now explicitly reports missing camera/location permission: consider the existing approved permission guide, never a bypass of attendance checks.
- Meeting audio fails in other ordinary applications on the same device: consider approved device-audio guidance only if the admitted scope allows it.
- An app explicitly requires an update, storage explicitly reports exhausted quota, or an available printer has a stuck queue: consider the corresponding reviewed guide.
- No distinct eligible alternative, blocked steps, changed symptoms, unknown outcomes or exhausted attempt budget: refer to native support, not random guidance.

The issue retains a bounded structured attempt ledger: guide ID, purpose, reported outcome and fixed follow-up choices. It does not imply verified guide navigation; that remains the native receipt contract. Only the student explicitly reporting that the original task works is a reported resolution. Protected exam, unexpected verification, account restriction and verified-recovery safeguards remain higher priority. No real tickets or guide content are created.

## Other accuracy refinements

- Ask about the actual remaining network symptom instead of always selecting general connectivity guidance.
- Normalize sentence-ending punctuation without losing dotted error signatures, preserve documented spaced code formats before possible-OTP filtering, and keep ordinary credential-status descriptions without requesting passwords.
- Distinguish explicitly requested setup from a report that Authenticator is already set up or not configured. Do not treat a vague mention of setup as authority to open a setup guide.
- Do not produce an exact factual answer if the input contained screened private information.

The original native catalog and existing safety policies still govern real deployment. These changes use generic reviewed-purpose references; availability and actual content mapping remain pending. Existing regression expectations must be updated later for the new network questions, failed-guide continuation and rank ordering. No tests, syntax checks, builds, browser execution or live integration were performed.
